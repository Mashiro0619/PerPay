# v0.1.0

## Schema migration

This is the first public release. A new data volume is initialized directly at database schema 13. There is no supported upgrade path from an earlier public release, and databases created by unpublished development builds are not accepted as release-compatible input. Preserve any such database outside both managed volumes before starting the release image.

Supported database schema range: `13..13`.

## Upgrade and rollback risk

There is no previous public image to roll back to. Before replacing any development deployment, create a verified current-state backup, copy it outside both managed Docker volumes, and retain the exact image reference and backup SHA-256. Restoring an older backup after new writes have occurred creates divergent histories and is not a lossless rollback.

## Operational notes

The release supports `linux/amd64` and `linux/arm64` images. The attached Compose uses the same image for the long-running `app` and `backup` services and for the opt-in one-shot `maintenance` profile. It declares two persistent named volumes: `perpay-data` for the active SQLite database and migration restore points, and `perpay-backups` for verified local SQLite backups, backup state, and the backup lock. Local backups are plaintext and both volumes normally reside on the same Docker host; they do not constitute encrypted or off-host disaster recovery.

Strictly unique, conflict-free collection-code matches are confirmed automatically with `payment_basis: INFERRED`; amount inference is not provider-issued order proof. Unmatched, ambiguous, conflicting, late, duplicate, debit, and amount-mismatch facts remain unconfirmed for explicit exception handling. The normal payment path has no proposed/review state or administrator confirm/reject action.

The attached Compose must contain the required secret configuration. The initial administrator password should be removed after the administrator has been created. API client key fingerprints, checkout token key versions, per-checkout terminal observation policies, ledger conflict operations, financial operations, and payment evidence remain immutable history. Readiness, new order creation, and payable public checkout instructions remain blocked until both provider collection and automatic reconciliation have a recent success, and again whenever either success exceeds the configured maximum age. Terminal checkout state remains readable during such an outage; operators must inspect the authenticated system status for collection and confirmation diagnostics.
