# PerPay 1.0.0

PerPay 1.0 提供完整的自托管支付宝收款流程：业务网站创建订单，顾客按收银台金额付款，PerPay 自动查账确认并发送通知。一个后台可管理多个业务网站和支付宝账号，支持原生 API 与易支付 V1/V2。

## 1.0 的主要能力

| 能力 | 使用方式 |
| --- | --- |
| 多网站、多账号 | 网站独立管理密钥、订单与通知，按指定、随机或权重分配收款账号。 |
| 查账与人工复核 | 通过支付宝官方 SDK 查询账务明细；按账号、金额和时间确认订单，异常付款保留流水和处理记录。 |
| 三种接入协议 | 接入助手给出原生 API、易支付 V1/V2 的服务地址、客户端 ID／PID 和密钥；可用 Node Demo 完成下单、付款和通知检查。 |
| 日常管理 | 查看趋势、筛选订单、导出 CSV、重发通知、追溯审计记录。 |
| 自托管维护 | 自动备份、异地保存与恢复工具，支持固定版本升级和回滚。 |

## RC4 以来的改进

### 配置与业务接入

- 首次向导逐项列出还没填的应用信息、密钥和收款码。连接检查后，可继续接入所选业务网站，完成付款和通知检查。创建账号后没收到响应时，用原请求重试会找到同一账号。
- 新网站创建后进入接入配置；没有可用收款账号时，可直接前往配置账号。密钥在独立弹窗中查看和复制，页面按现有密钥的状态提供生成或更换操作。
- 切换网站接入设置的分组时，保留尚未保存的内容。删除没有业务记录的网站后，清除其草稿和侧栏选择并返回列表；取消删除或删除失败时保留草稿。正在保存易支付配置时，不能同时删除该网站。
- 账号配置、更换密钥、删除或 IP 白名单保存遇到版本冲突时，可重新读取最新配置，并核对保留的填写内容；修复未完成账号配置时连续更换密钥失败。
- 服务器明确拒绝创建测试订单时，可修改网站和金额；没有拿到明确结果时，保留原请求供核查和重试。
- 重整 README、部署、接入、维护和开发文档，补齐配置步骤与错误处理，更新界面截图。

### 收款与订单处理

- 正常查账已覆盖需要核对的时间段，而且结果仍在有效期内时，即使正在分段补查历史记录，也继续接受新订单。历史补查不会延长正常查账结果的有效期。
- 同一账号、同一环境更换 App ID 后，可核对新应用查到的迟付款，并人工关联到旧订单；仍会阻止同一笔付款被同时确认给多笔订单。
- 争议订单可在核对可用收入流水、填写理由后重新确认，保留原关联、撤销和通知历史。每次确认时保存当时的金额，历史统计读取这份金额，后来重新确认不会改写过去日期的数据。
- 撤销收款确认后，不再重发原来的易支付成功通知。手动重发通知会打开这次发送的记录，可在原记录和最新结果间跳转；登记外部退款后，可逐条忽略已核对的争议提醒。
- 订单区分待付款、过期未付款和关闭未付款，保留商户订单号及独立退款标记；同名收款账号也能区分。CSV 可按创建日期范围导出，并标明收款账号和金额单位。
- 每日趋势完整展示所选日期范围。手机收银台补齐从相册扫码的步骤；本机通过 HTTP 试用易支付收银台时，仍可返回商家页面。
- 待处理列表优先展示需要人工处理的事项。清空搜索后不再残留旧关键词，复制提示对应实际复制的内容；窄屏和放大文字下，搜索、协议选项与操作提示仍能完整阅读和使用。

### 长期运行与备份

- 一次查账成功结束、且结果只有一页时，其中的空结果和重复流水副本保留 7 天，后台每小时分批清理；首次入账的来源记录、异常与各账号最近的查账记录继续保留。
- 查账和对账正常且结果没有变化，或这一轮没有待发送通知时，将记录按小时汇总，减少日志增长。
- 临时空间足够时，备份会去掉副本中已经空出来的数据库页，缩小文件（SQLite 压实）；空间不足以压实时，仍保留完整快照。只有通过最终校验的文件才会成为可用备份。
- 新增查看数据库空间占用和停服压实的工具。程序运行时要求的最低可用磁盘空间设为 64 MiB，备份另外检查目标目录的空间，避免仅因数据库较大就提前停止收款。
- 等待下一次备份时，进程最多间隔 30 秒重新读取策略，并调整执行计划。备份或校验失败时，后续清理出错不会把原定重试时间向后推；如果只有清理出错，备份仍按正常周期运行。
- 备份页面集中显示当前任务、最近一份备份和下次执行时间；查账诊断和审计详情先说明实际结果及失败原因。
- Compose 三个服务共用 `x-perpay-image`，发布附件固定对应镜像；恢复指南覆盖新服务器导入备份与原主密钥。

## 升级与恢复

本版的数据库结构版本（schema）为 **44**，兼容范围为 **24—44**。从 RC4 的结构版本 42 升级会依次执行迁移 43、44，增加查账历史清理所需的状态和索引，并允许争议订单重新确认收款；已经使用结构版本 44 的开发版本无需再次迁移数据库。

1. 使用原版本完成备份，单独保存原主密钥（`PERPAY_MASTER_KEY` 或 secrets 卷中的 `master-key`）。
2. 若存在同一付款跨应用重复确认，先按[历史重复收款关联检查](https://github.com/Mashiro0619/PerPay/blob/v1.0.0/docs/maintenance.md#历史重复收款关联的升级检查)处理并重新备份。
3. 停止应用和自动备份：`docker compose stop app backup`。
4. 将 `x-perpay-image` 改为 `ghcr.io/mashiro0619/perpay:1.0.0`。旧 Compose 配置需统一修改 `app`、`backup`、`maintenance` 三处镜像。
5. 执行 `docker compose pull`、`docker compose up -d`，检查迁移、查账、通知与备份状态。

回退到 rc.4 或更早版本，须恢复目标版本兼容的升级前备份和原主密钥。升级后已有新交易时，先保留当前完整数据。

清理查账历史后，空出来的数据库页会留给后续数据复用。需要真正减小主库文件时，先停服，再按[数据库空间与压实](https://github.com/Mashiro0619/PerPay/blob/v1.0.0/docs/maintenance.md#数据库空间与压实)操作。

新部署下载本版 `docker-compose.yml`，按[部署说明](https://github.com/Mashiro0619/PerPay/blob/v1.0.0/README.md)启动。支付宝应用须已上线，并具备对应收款账户的账务明细查询权限。
