# PerPay 1.0.0

本说明对应开发分支，**不表示版本、标签或镜像已经发布**。

## 多业务网站

- 多个自有网站共用现有经营收款码、支付宝开放平台应用及采集对账流程。网站不是独立支付宝账户，也不提供独立结算。
- 每站独立 API 和通知密钥、订单权限、通知／返回来源、接单状态、待付款上限、订单策略及收银台展示。
- 客户端身份来自已验证的 HMAC 签名。网站间可以使用相同商户订单号、幂等键和 nonce；跨站查单、关闭和事件读取均隔离。
- 金额按全局完整应付金额分配，优先最小可用尾差；复用遵守上一笔订单的冷却快照。网站上限不代表预留金额槽位。
- 通知按网站轮转领取、串行发送，保持租约、ACK、重试和人工重投保护。在途投递使用已捕获的密钥与策略；下一次尝试读取当前配置。
- 暂停只阻止新订单；旧单继续查询、付款、对账和通知。关闭通知保留任务，不自动复活死信。只允许删除无历史数据的网站，身份保留墓碑。

## 一级汇总与二级网站后台

同一个管理员账号管理全部网站。`/admin/` 固定全局汇总，`/admin/sites/:clientId` 改为网站概览；原编辑入口移到 `settings/:section`。订单、通知、待办及财务操作使用路由绑定的网站范围，统计和列表不再要求逐页选择网站。旧业务页面的 `?api_client_id=...` 转为二级路径，保留筛选但清除旧分页游标。共享账本、运行状态和实例设置只保留在一级。

新增 `/api/admin/v1/sites/:clientId/` 下的网站业务接口，网站身份只取路径，不允许正文或查询参数再指定 `api_client_id`；越界资源返回 404，共享／跨站收款证据冲突返回 `site_scope_conflict`。全局管理员接口保持可用；`sites/overview` 分页批量聚合各站指标。此两级后台改造不新增数据库迁移，不改变 schema 34、支付签名或历史数据。

## 设置与破坏性变更

- 支付宝接入、经营收款码和采集设置独立保存。有效期、尾差、冷却、上限在业务网站设置，采集间隔和安全延迟属于 PerPay 实例策略。
- 默认模板仅预填以后创建的网站；已有网站保存完整配置，不继承模板变更。
- 单站专用密钥和通知管理写接口返回 `410 / site_settings_moved`；旧混合字段返回验证错误。请同步更新管理客户端和自动化脚本。
- 全局管理员测试收款必须提供 `api_client_id`；全局按商户订单号管理查询必须指定网站。网站作用域接口改由路径固定网站，不能重复提交身份字段。业务接口不得用请求正文选择网站。
- `/api/v1/system/status` 仅返回本站的 `status`、`code`、`client_id`、`accepting_orders`、`notifications_enabled`。采集、备份及全局统计只对管理员开放。
- HMAC 请求签名、通知签名、业务支付路径与收银台 capability 保持原协议。升级实例的 `default` 是保留的旧网站 ID，不是默认回退或特殊权限。

## 数据库与升级

最新数据库 schema 为 **34**，运行兼容范围为 **24—34**。本次新增迁移 34，不修改历史迁移。历史迁移 24—34、迁移 27—34 均依次应用；备份及维护工具检查范围但不代替应用执行迁移。

迁移事务保留旧网站的明文密钥值、指纹、密钥版本、通知 `key_id` 和内部主键；业务密文改为绑定实例、网站、用途和版本。订单金额、策略快照、原二维码关联、通知正文及签名证据不重写。旧通知 origin 同时初始化为通知和返回 origin，之后可分别修改。缺失必要主密钥、错误主密钥或损坏数据会使迁移回滚；从未签发的密钥不会自动补发。

1. 核实目标构建及镜像已实际可用。发布后的目标标签为 `ghcr.io/mashiro0619/perpay:1.0.0`，也可固定经验证的镜像摘要；不要将开发文档中的目标标签当作已发布镜像。
2. 先使用旧版本备份，单独安全保管 `PERPAY_MASTER_KEY`。停止所有写入进程：
   ```sh
   docker compose stop app backup
   ```
3. 将 app、backup、maintenance 指向同一份支持 schema 34 的构建，保留原数据卷、主密钥、域名、代理和白名单配置。必要的离线备份／恢复操作也必须使用匹配数据库版本的维护工具。
4. 只启动 app，等待事务迁移完成，验证管理员登录、原网站密钥、历史订单及二维码、采集对账和通知。核实设置拆分后的参数没有变化。
5. 验证新网站独立接入、严格健康与就绪检查和隔离备份恢复，再启动 backup。不要用真实流水进行破坏性测试。

**不能将 schema 34 数据库交给 0.3.2 或更旧程序打开。** 回退必须恢复升级前备份及原主密钥；禁止手改 schema 版本、删除游标或手动改写业务密文。升级后产生新交易时，不应直接用旧备份覆盖，应保留完整数据和证据，使用支持新结构的修正版处理。

详见[接入文档](../../USAGE.md)和[维护与恢复](../maintenance.md#固定版本与回滚)。
