# PerPay 0.3.2

本版在 0.3.1 基础上增加管理员 IP 白名单、收银台手动核实与查账最小间隔，并改进应付金额的尾数分配、请求频率限制和异常说明。

## 主要变化

### 管理员 IP 白名单

- 支持 IPv4、IPv6、IPv4-mapped IPv6 和 CIDR，默认关闭。保存时检查新规则仍允许当前来源，成功后立即生效。
- 限制管理页面、资源、登录、初始化和管理 API；公开收银台、业务 API、回调和健康检查保持原访问规则。
- 根据 `PERPAY_TRUSTED_PROXY_CIDRS` 指定可信代理，再从这些代理提供的信息中识别客户端地址。
- 被白名单挡住时，可停服运行命令关闭白名单。原规则、密码、登录会话和数据保留，并记录操作审计。[白名单恢复](https://github.com/Mashiro0619/PerPay/blob/v0.3.2/docs/maintenance.md#管理员-ip-白名单与离线恢复)

### 收银台查询与采集调度

- 待付款时约每 2.5 秒读取 PerPay 订单状态；点击手动核实按钮，会通过 `POST /api/public/v1/checkouts/:token/check` 请求查账，并遵守间隔与频率限制。
- 查账排队或执行中返回 202，多个收银台的重复请求合并处理。按钮最多显示等待 30 秒，之后页面仍会在后台更新结果。
- 新增 `minimum_scan_interval_seconds`，满足 **5 ≤ 最小间隔 ≤ 活跃间隔 ≤ 常规间隔 ≤ 3600 秒**，按上一轮完成到下一轮开始计算。
- 自动与手动查账共用最小间隔、请求频率限制、失败后的重试等待时间，以及未完成页面的继续查询规则。修改配置或重启服务，都不会跳过已经安排的等待时间。
- 修复主动取消后等待过久、已完成任务继续占用临时容量，以及调度信息保存失败后无法正确继续的问题。

### 尾差、可用性与异常诊断

- 在未被其他订单占用、且已满足冷却要求的尾数中，优先使用最小值。例如已冷却的 `.01` 优先于未用过的 `.05`；历史订单已保存的金额和冷却设置保持不变。
- 收银台 token 无效时也限制请求频率，404 和 429 错误页使用更少资源。
- 公开健康检查会缓存数据库结构检查和就绪检查的结果，最多 1 秒；下单、管理和维护操作仍会重新严格检查。
- 运行状态显示查询失败的时间范围、正常查账或补偿查账类型、连续失败次数，以及下一次实际计划；连续失败达到 3 次时告警。
- 分别显示等待存储恢复和等待支付宝查询的状态，保留失败原因及继续处理的入口。
- 更新组件样式并精简白名单页面说明。

## 数据库与兼容性

本版的数据库结构版本（schema）为 **33**，兼容范围为 **24—33**。从 0.3.1 升级执行迁移 32—33：新增默认关闭的 IP 白名单、最小查账间隔，并把查账需要等待到何时写入数据库。旧实例的最小间隔沿用原活跃间隔。

订单、流水、金额、已保存的冷却设置、密钥与审计记录保留。旧设置请求省略最小间隔时保留已有值，其他间隔与之冲突时返回错误。手动核实进度只表示这次查询的执行情况；业务网站仍须查单或验证付款通知的签名，再判断付款是否完成。

## 升级与回滚

1. 备份数据库，另存原主密钥和部署配置。
2. 将三个服务统一设为 `ghcr.io/mashiro0619/perpay:0.3.2`，保留自己的域名、代理与数据卷设置。
3. 在原部署目录执行：

   ```sh
   docker compose pull
   docker compose stop app backup
   docker compose up -d
   docker compose logs --tail=100 app backup
   ```

4. 核对结构版本 33、管理员登录、查账、自动确认与备份。启用白名单前检查识别 IP 和可信代理配置，再完成小额收款与通知联调。

回退到 0.3.1 或更旧版本需恢复兼容的升级前备份和原主密钥；升级后已有交易时先保存当前完整数据。

查账持续失败时，保留失败的查询时段和相关请求、响应记录，按[查账恢复](https://github.com/Mashiro0619/PerPay/blob/v0.3.2/docs/maintenance.md#采集持续失败)排查。删除分页位置、跳过失败页或把未完成的查询分段强行标为完成，会造成漏账。
