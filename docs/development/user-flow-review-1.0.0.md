## 1. [P1] 过期或关闭不代表付款结果已终结，收银台却停止查询

**复现**：用户在截止前付款，账单尚未采集；下一次收银台查询先返回 `EXPIRED / UNPAID`，随后服务端确认之前按时付款的流水。

**当前行为**：前端 `interval()` 对 `EXPIRED / CLOSED` 返回 `null`，页面不再查询；已有订单的这些状态也没有“查询付款状态”按钮。没有配置返回地址或帮助地址时，页面没有业务操作出口。即使有返回商家入口，当前收银台仍不能显示随后确认的结果。

**用户影响**：已经正确付款的用户会持续看到过期/关闭结果，需要自行刷新整个页面或另找商家核查。

**证据**：

- `web/src/checkout/controller.ts:75–82`：终止关闭/过期状态的轮询；恢复可见和联网时也依据同一 `interval()` 判断。
- `web/src/checkout/CheckoutApp.tsx:125–128`：关闭/过期订单没有状态查询操作。
- `test/reconciliation-store.test.ts:497–515`：服务端仍能确认关闭/过期后才发现的、实际按时付款的流水。
- 临时 Vitest 场景推进 90 秒后，输出 `{ fetches: 1, visual: 'EXPIRED' }`；期望随后观察到 `CONFIRMED` 的断言失败。另一条期望过期后仍保留状态查询按钮的断言失败。
- 后端“及时付款在关闭/过期后发现”两项测试通过，验证这不是服务端禁止的状态变化。

**建议**：付款入口到期立即关闭；付款结果查询在公开链接观察期内继续，允许低频轮询和手动 GET 查询。不要因停止付款就停止观察收款结果，也不要为终态查询重新提交付款核实 POST。

## 2. [P2] 离线保存后选择放弃，恢复网络仍会自动提交

**复现**：修改实例经营码/支付宝/采集配置 → 离线 → 点击保存 → 切换页面，确认“放弃修改并继续” → 恢复网络。

**当前行为**：保存使用默认在线 mutation，离线时进入暂停队列。编辑器卸载仅设置 `mounted=false` 并抑制回调，没有取消排队；联网后仍发送请求。离开确认框却明确承诺“此页面的修改不会保存”。

**用户影响**：用户认为已放弃的设置可能稍后改变运行中的收款配置；留在页面时则一直显示保存中，无法继续编辑。待办批量忽略也使用相同默认排队策略。

**证据**：

- `web/src/components/SettingsForms.tsx:299–325,336–342`。
- `web/src/drafts.tsx:133–146`：放弃后的提示与实际行为不一致。
- `web/src/pages/WorkItems.tsx:75`：批量忽略 mutation 未指定网络模式。
- `web/src/api/client.ts:133`：全局仅设置 `retry: false`，不禁止离线暂停与联网续发。
- 使用当前安装的 QueryCore，无网络复现：离线提交为 `calls=0, status=pending, isPaused=true`；移除 observer 模拟离开后队列仍有一项；联网后无再次提交即 `calls=1`。

**建议**：沿用密码/白名单和固定财务操作的策略，禁止离线排队，离线提交立即提示并保留草稿；联网后由用户明确再次提交。不要把 `retry: false` 当作禁止离线续发。

## 3. [P2] 正常跨组编辑网站配置，会反复产生版本冲突

**复现**：基本信息改名并保存 → 订单设置修改有效期并保存 → 返回基本信息再次改名保存。

**当前行为**：每组独立缓存且无限新鲜；保存仅更新当前组缓存。第三次保存使用基本信息组保留的旧 revision，收到 409；重复保存继续提交旧 revision。设置页没有刷新/重新读取配置的恢复入口，需刷新整个页面并重新录入。

**用户影响**：没有其他管理员参与，普通顺序编辑也会被当作并发冲突；保存后跨组返回还会显示过时配置。密钥轮换增加版本后也会影响其他已缓存分组。

**证据**：

- `web/src/pages/Sites.tsx:152–156`：包含 section 的独立缓存与 `staleTime: Infinity`。
- `web/src/pages/Sites.tsx:207–209`：本组保存快照与草稿。
- `web/src/pages/Sites.tsx:231–239`：只更新当前分组。
- 临时合成 API 测试复现请求 revision `[0, 1, 1, 1]`，服务器已为 2；两次返回基本信息后的保存都冲突。

**建议**：统一网站配置缓存，或保存/轮换后使全部分组取得一致快照；提供保留草稿、重新读取和核对的冲突恢复。不能只给旧完整配置换上新 revision，否则可能覆盖其他组已保存内容。

## 4. [P2] 一级人工关联没有展示订单所属网站

**复现**：两个网站分别有相同商户订单号。管理员在一级共享账本为网站 A 核对收款，搜索该商户号，选择订单，再进入人工关联确认。

**当前行为**：候选只显示商品、应付金额、创建时间、收银台状态和商户号；没有网站身份或可见的唯一订单标识。最后确认虽然已读取包含 `site_name` 的管理员订单，`OrderFacts` 仍不显示网站。候选的服务端对账投影本身也缺少网站字段。

**用户影响**：管理员不能在关联操作内依据所属网站核对订单，只能退出补查；未核对就确认可能关联到其他网站的订单。

**证据**：

- `web/src/components/detail/ManualCandidatePicker.tsx:83–94`。
- `web/src/components/detail/DetailPrimitives.tsx:160–192`。
- `web/src/pages/FinancialDialog.tsx:304`：最终确认使用不带链接的 `OrderFacts`。
- `src/reconciliation/store.ts:113–131`：对账订单投影没有网站身份。
- 临时组件测试使用重复商户号、不同应付金额的跨站订单；候选没有 A/B 名称。选择订单与流水后，最终响应包含网站 A，确认按钮可用，但页面仍找不到网站 A；期望显示身份的断言失败。

**范围说明**：不声称默认配置下两个并发订单一定同分钟、同应付金额；全局金额占用会分配不同尾差。问题是缺少判断归属所需的网站信息。

**建议**：候选和最终确认均显示网站名称；必要时用客户端 ID/订单 ID 辅助区分。保留服务端既有归属校验，同时补足一级管理员作出选择的信息。

## 5. [P2] 跨站恢复测试收款后，“查看订单”进入当前网站而非原网站

**复现**：A 网站测试收款响应丢失 → 切到 B → 打开测试收款 → 明确重试原请求并成功恢复 A 的订单 → 在确认/过期/错误等不能继续付款的状态点击“查看订单”。

**当前行为**：请求和结果查询正确固定在 A；fallback 详情链接却使用当前路由自动补范围，生成 B 的订单地址，得到 404。可付款分支已经使用固定 `orderHref`，只有 fallback 不一致。

**用户影响**：用户按提示完成恢复后，关键核查入口反而显示订单不存在，难以确认原收款结果。

**证据**：

- `web/src/components/test-payment-result.tsx:36,214,245`。
- `web/src/lib/test-payment-request.ts:168–171`：未知结果时保持原请求所有者。
- 临时完整组件流程中两次 POST 都是 `/sites/a/test-payments`，成功后界面显示收款已确认；详情链接实际是 `/sites/b/orders/<A订单ID>`，期望 A 地址的断言失败。

**建议**：所有查看详情入口都使用固定 `orderHref` 和 `global`，不要从当前工作空间推导已提交请求的订单归属。

## 6. [P2] 通知密钥轮换提示错误地承诺旧密钥立即失效

**复现**：管理员看到网站密钥卡片“轮换后旧密钥立即失效”，轮换通知密钥，并据此立即在接收端移除旧密钥。

**当前行为**：该提示同时覆盖 API 和通知密钥；实际已在途通知继续使用捕获的旧密钥，下一次尝试才使用新密钥。

**用户影响**：按提示切换接收端会拒绝仍合法的旧签名通知，可能进入失败/死信，增加人工重投与接入排查。

**证据**：`web/src/pages/Sites.tsx:517–518`；`src/notifications/site-processor.ts:33–51`；`test/site-notifications.test.ts:138–159` 已验证在途签名快照与重试切换。

**建议**：分别说明 API 密钥立即退役、通知在途请求保留旧签名；通知轮换确认中明确接收端过渡要求。

## 7. [P3] 官方 Demo 指导先启用通知，漏掉必须先生成密钥

**复现**：新建网站后，按调用端 Demo README 第一步启用通知、填写来源并保存，期待取得通知签名密钥。

**当前行为**：1.0 保存不会自动生成密钥；服务端先返回 `site_secret_missing`，要求先生成通知签名密钥。

**用户影响**：新用户照官方接入步骤操作就被阻断，必须自行倒推操作顺序。

**证据**：`examples/node-client/README.md:7` 与 `src/sites/store.ts:107–108`。

**建议**：明确进入“网站设置 → 接入与通知”，先生成通知密钥并配置接收端，再设置来源、开启通知和保存；API 密钥也应写出显式生成入口。
