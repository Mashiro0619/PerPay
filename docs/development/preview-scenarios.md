# 本地演示场景

在仓库根目录执行 `npm run build` 和 `npm run demo:preview`，访问 `http://127.0.0.1:6192/admin/`，密码为 `123456`。默认只保留这一个预览入口，同时提供页面和演示 API。
更新预览时停止旧演示进程、重新构建，并在同一端口重启；服务在启动时读取管理端静态资源，单独刷新浏览器不会替换旧构建。不要通过递增端口叠开预览实例。只有明确需要前端热更新时，才使用 `PERPAY_DEV_API_URL=http://127.0.0.1:6192` 和 `npm run dev:admin` 的开发组合。

需要在本地预览实际检查官方版本时，使用 `npm run demo:preview -- --official-updates`。该选项仅启用 GitHub 官方版本元数据查询；付款、支付宝查账、通知及配置写入仍不执行。默认测试预览不连接外部服务。

每次启动会重新生成独立临时数据。所有金额、付款人、通知响应及收款凭据均为模拟，页面保持只读，默认不调用外部服务；启用 `--official-updates` 后仅查询 GitHub 版本元数据。订单、账本、通知及人工处理历史通过项目的领域方法建立，并执行数据库完整性检查。

商户订单号使用 22 位纯数字字符串，由北京时间的创建日期时间和业务流水组成；流水号和支付宝交易号分别使用 24 位、28 位数字字符串。各来源使用独立序列，避免碰撞，所有编号保持字符串以保留精度。付款人使用“陈*安”“林*宁”等固定的虚构脱敏姓名，网站、商品及备注使用日常业务内容；页面不显示演示徽标、说明弹层或收银台横幅，演示属性保留在响应头、内部页面属性及原始证据中的 `synthetic` 字段，不把场景代号当成业务数据。

日常交易覆盖近 90 天，按星期、缓慢的业务增长和确定性波动安排笔数与商品组合；当天仅生成已经发生时段的数据。特殊订单分散在最近 30 天，付款确认、相关流水和通知历史跟随各自业务时间推进。通知示例采用 29–199 元的常见价位，大额订单示例为 999 元，避免将所有测试情况集中到当天造成统计尖峰。

## 从完整订单开始

概览最近订单的第一笔是“轻账桌面版 · 终身授权”，可通过启动日志的 `featured` 或 `scenarios.lifecycle.fullEvidence` 精确定位。该订单同时包含收款流水、自动关联、付款确认、通知投递和回执证据。页面显示实际生成的数字商户订单号，可在概览或详情读取后搜索。

待支付、已取消、过期未支付的订单保留合理的空收款状态；订单未要求回调时，通知区也会为空。它们是用于查看空状态的独立场景。

启动日志中的 `scenarios` 给出本次生成的订单、流水、冲突和通知 ID。订单页面为 `/admin/orders/:orderId`，网站后台为 `/admin/sites/:clientId`。重启后 ID 和登录会话会更新。

## 订单与收银台

下表使用启动日志中 `scenarios.lifecycle` 的键定位场景；键仅用于开发验收，不显示为订单号或商品名。

| 日志场景键 | 场景 |
| --- | --- |
| `fullEvidence` | 自动确认收款、通知成功、订单返回地址 |
| `open` | 待支付和可打开的收银台 |
| `expiringSoon` | 启动时约剩两分钟的付款倒计时，随后自然过期 |
| `expired` | 已过期未付款 |
| `closed` | 主动关闭未付款 |
| `disputed` | 近期撤销收款关联，可查看争议收银台 |
| `notificationFailed` | 收款成功，通知停止重试 |
| `notificationRetry` | 收款成功，通知等待重试 |
| `noNotificationRequested` | 订单未配置回调地址 |
| `notificationsDisabled` | 网站未开启通知 |
| `smallAmount`、`largeAmount` | 一分钱与大额订单 |
| `longDescription` | 长商品名、长备注、中英文混排 |
| `limitedFirst`、`limitedSecond` | 达到网站待支付笔数上限 |
| `pausedSiteHistory` | 暂停接单的网站仍能查看历史付款 |

财务和通知订单分别通过 `scenarios.financial`、`scenarios.notifications` 定位。它们与日常订单使用一致的数字编号和商品名称样式，可进入对应网站缩小列表范围；异常原因和投递结果由实际状态及处理记录表达。

## 财务与通知

全局支付宝流水列表为 `/admin/ledger`，详情为 `/admin/ledger/:ledgerEntryId`。启动日志的 `scenarios.ledger` 包含跨来源重复采集：`identical` / `identicalCopy` 内容指纹一致，只展示一笔；`inconsistent` / `inconsistentCopy` 金额相差一分，金额显示待核对，详情保留两个版本。这两笔均未关联订单；已收款订单的关联仍来自原始生效凭据。两个来源都属于沙箱，先建立历史来源，再启用当前配置来源，造数结束保持当前来源，不生成新的收款关联。生产与沙箱隔离、多个生效关联等边界由后端与 API 自动化测试覆盖。

财务场景展示人工关联和撤销的凭据、争议处理、未匹配或异常流水、同价订单和金额复用、账本冲突的开放与处理历史，以及待办提醒的忽略与恢复。退款使用当前版本支持的人工退款标记及撤销历史；不会创建已停用的旧版退款记账操作。

通知场景覆盖待投递、投递中、等待重试、已确认和停止重试，以及临时失败、永久失败、结果未知、失败后恢复与人工重新投递。每条通知都关联实际生成的订单事件和尝试记录。

演示不会运行后台投递或支付宝查询任务；“投递中”等状态是便于查看的模拟快照，时钟和付款倒计时会继续前进。健康状态在响应头标注为模拟。界面不额外展示演示身份提示，更新检查根据是否启用 `--official-updates` 返回实际官方查询结果或不可用状态。

## 验证

`test/preview-demo.test.ts` 验证会话、只读保护、隔离、导出、禁止外部请求、付款人多样性和午夜附近的时间顺序。
`test/preview-scenarios.test.ts` 验证各场景的真实 API 投影、商户号格式和唯一性、通知载荷中的订单号一致性、收款与通知关联、多网站边界和数据库完整性，并检查 7/30/90 天统计一致、场景日期分布、当天收入及订单集中度、历史波动与未来时间。

造数时还发现一项现有校验问题：带关键词或网站筛选的批量忽略会将 `q` / `api_client_id` 计入操作摘要，但 `admin-operation-integrity.ts` 重建摘要时缺少这两个字段。演示使用按类别批量忽略、随后逐条恢复的有效操作路径建立提醒历史；该筛选操作的审计问题需要单独修复。

修改后运行：

```sh
npm run typecheck
node --experimental-strip-types --test --test-isolation=process test/preview-demo.test.ts test/preview-scenarios.test.ts
```
