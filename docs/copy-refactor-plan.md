## 1. 目标与非目标

### 1.1 目标

- 用户能读懂每一条界面文案：知道发生了什么、为什么、下一步做什么。
- 同一个概念只有一个词；界面、文档、错误信息一致。
- 数据来源清楚：支付宝数据、PerPay 数据、业务网站数据不混在一起。
- 文档保留技术深度，但先给结论，再给细节。

### 1.2 非目标

- 不重做 UI，不新增功能，不调整信息架构（第 2B 批的少量分组除外）。
- 不把中文文档翻译成英文；OpenAPI 已决定保留现有语言分布，不批量翻译。
- 不改 API 契约。AA-11 字段统一已决定暂缓，见第 8 节。
- 不改数据库、迁移、账务规则、通知协议。

### 2.2 数据来源

| 来源 | 典型数据 | 写法 |
| --- | --- | --- |
| 支付宝 | 支付宝订单号、支付宝交易时间、支付宝交易金额、支付宝交易对方、支付宝交易备注、支付宝商户单号、收支方向、经营码、App ID、支付宝公钥 | 字段名带「支付宝」，或整块放在「支付宝流水」分组 |

三条硬规则：

1. 同一屏出现两个来源，必须有分组标题或字段前缀。
2. 独立展示或与其他来源并排的支付宝原始字段带「支付宝」前缀；整块来源明确时可由「支付宝流水」标题承接。不要用「流水商户单号」这种半前缀，也不要把 PerPay 内部流水 UUID 标成支付宝流水号。
3. PerPay 的判断要带依据：自动推断写「按金额和付款时间推断」，人工关联写「管理员人工关联」，**不要给人工关联也套「推断」**。

另外：**来自支付宝的数字有延迟**（查账间隔 + 查账延迟），不能让人以为是实时余额。展示口径见 AA-17。

### 2.3 语言分层

- **界面**：白话。标题用名词，按钮用动词；状态标签 ≤ 6 个字；原因和下一步放正文。
- **文档**：可以先给技术细节，但每个术语首次出现给一句定义；不要用「不是…也不是…」堆否定。
- **错误信息**：先说是哪一步失败，再说怎么办；不把内部错误码直接给用户。

### 2.4 句式

- 一句话最多两个条件；超过就拆。
- 不用三重否定；先说「是什么」，再说「不是什么」。
- 不用「尚未 / 予以 / 进行 / 确保」这类公文词，除非是法律/安全表述。
- 数字与单位之间加空格：5 秒、10 MB、100 条。
- 中文与行内代码之间加空格：`client_id` 字段。

### 2.5 工程约束

- 不改接口字段、数据库、账务规则；第 2C 批已决定暂缓。允许本计划需要的草稿受控 props（`secondsDraft` / `onSecondsDraftChange`）、formatter、精确单位换算、来源分组及明确的错误状态分支。两个父编辑器已直接从 raw 推导 dirty/error，不补无用的 `onDraftStateChange`。
- 固定展示名称若参与持久化请求指纹，改名必须保留旧请求的精确重放。管理员测试单旧名 fallback 是已完成的兼容修复；普通订单指纹、其他请求字段、权限和准入检查不可放宽。
- 改按钮文字时，同步改 `aria-label`、`title`、测试断言，避免读屏和测试对不上。
- **允许新增行为测试**：输入换算、输入限制、导航变化必须有对应测试（例如 5123 毫秒的往返、500 个 emoji 的边界、多站/单站链接）。
- 现有断言只能更新期望文案，**不能删除、跳过或放宽**。
- 沿当前分支按单一职责拆分 SSH 签名提交，源码与必要回归一起提交；不为满足早期“一批一个提交”模板重写已有历史。格式见第 7 节。

### 3.0 撤销项：退款备注上限

原计划要求把 `web/src/pages/RefundMark.tsx:326` 的 `maxLength={1000}` 改成 500。**撤销，不要改。**

原因：

- 校验函数 `web/src/lib/refund-mark.ts:9` 用 `Array.from(note).length > 500`，按 **Unicode 码点**计数。
- HTML 的 `maxLength` 按 **UTF-16 长度**计数。500 个 emoji 正好是 1000 个 UTF-16 单元。
- 现有测试 `web/test/refund-mark.test.tsx:153` 明确要求接受 500 个 emoji；改成 500 会把容量减半。

如果以后要改，正确方向是统一计数口径，而不是改 `maxLength`。

### 3.2 特殊实现说明

**第 2 条：通知超时改为秒，必须保留毫秒精度并拒绝超精度**

后端字段是整数毫秒，合法值不一定是 1000 的倍数（例如 `5123`）。因此：

1. 如果保留受控 number input，给内部 `NumberField` 增加可选 `step?: number` 和 `validate?: (raw: string) => string | null`；如果改成字符串草稿，单独实现 `SecondsField` 也可以。两条路都必须满足下面的行为。
2. 该字段用**本地字符串草稿**，不要直接把 `value={ms / 1000}` 交给 number input：

```tsx
// 父编辑器保存每次输入的 raw，并由它推导 dirty/error。
onSecondsDraftChange(raw);
if (siteTimeoutError(raw)) return; // 非法精度或范围不更新配置，保存禁用
const milliseconds = integerUnits(raw, 1000)!;
change((p) => {
  p.notification_delivery.timeout_milliseconds = milliseconds;
});
```

3. **不要用 `step={0.1}`**：`5123` 毫秒会显示成 `5.123` 秒，触发 `stepMismatch`，表单无法提交。`step={0.001}` 只用于原生校验，真正的合法性以 `integerUnits` 为准。
4. **不要静默四舍五入**：`5.1234` 必须显示「最多 3 位小数」并阻止保存，不能保存成 `5123`。
5. **草稿要放在父编辑器，不能只放在字段组件里**：`SitePolicyFields` 的分组是条件渲染的，`DefaultsEditor` 切标签时会把 integration 分组卸载，字段内部的 `raw` 会丢。当前实现由 `SiteEditor` 和 `DefaultsEditor` 各持有 raw，并用 `siteTimeoutError(raw)` 推导错误，通过受控 props 传给字段。切标签后草稿和错误仍在，无需额外的 `onDraftStateChange`。
6. **统一 dirty 要同时供离页保护和版本冲突处理**：`dirty = 配置有变化 || 草稿有变化`；`invalid` 单独传给保存按钮。`dirty` 要并进 `useDirtyDraft`，也要并进 `requiresReview`（现有版本冲突判断用到 `dirty`）；只改 `useDirtyDraft` 会漏掉版本冲突分支。
7. **区分合并与超时字段的明确取值**：自动 `applyReview`，以及应用无关字段的冲突选择，都必须保留非法 raw、错误和保存阻断。只有明确选择并应用超时字段的冲突值，才将非法 raw 归一化为所选毫秒值的秒表示；合法 raw 可与合并后的配置同步。保存成功或确认放弃后的重新挂载也可重置。不要用 `policy` 引用变化或无条件 `useEffect(value)` 清除非法草稿。`SiteEditor` 路由离开先经过草稿确认，`DefaultsEditor` 本地切标签不重置。
8. **验收（分开写）**：
   - `SiteEditor`：输入 `5.0004` 后切分组（路由变化）→ 弹离页确认；保存禁用。
   - `DefaultsEditor`：输入 `5.0004` 后切标签 → 不弹确认，草稿和错误保留，保存仍禁用；真正离开页面 → 弹确认。
   - 自动合并 / 应用无关冲突 → 原非法字符串与错误保留，保存仍禁用；强制触发表单提交也不发送请求。
   - 明确选择并应用超时字段的冲突值 / 保存成功 → 显示值与所选或已保存配置一致（`5` ↔ `5000`）。仅点击冲突选项、尚未应用时不重置输入。
9. **并发冲突界面**：`web/src/lib/site-configuration.ts:15` 把同一字段标成「通知超时（毫秒）」。表单改秒后，这里也要显示秒：在字段元数据里加一个 `format`（number → `5.123`），`SiteFieldConflict` 带上该 formatter，`SiteConfigurationConflicts` 渲染时调用；label 同步改「通知超时（秒）」。只改 label 不改值，会出现「5.123 秒」实际是 5123 毫秒的错位。
