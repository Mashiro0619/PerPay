# 易支付接入

PerPay 提供易支付 V1 和 V2 接口，支持支付宝网页收款。已有易支付插件的网站可填写 PerPay 网关、商户 PID 和对应密钥。商户 PID 固定绑定业务网站，更换原生 API 的客户端 ID 后仍使用原 PID。

## 配置网站

1. 为业务网站选择可用的支付宝账号和收款码。
2. 在「网站设置 → 接入与通知」保存通知来源，如 `https://shop.example.com`，并开启通知；需要返回商家时，再保存返回来源。
3. 在接入助手选择插件支持的协议，复制网关地址和商户 PID，通过凭据旁的「查看」取得密钥。
4. 将下表参数填入业务网站的支付插件，再从业务网站发起订单，核对收银台、付款结果和通知记录。

| 配置 | V1 | V2 |
| --- | --- | --- |
| 网关 | PerPay 服务地址，以 `/` 结尾，如 `https://pay.example.com/` | 同左 |
| 商户号 | 商户 PID | 商户 PID |
| 业务后端为请求生成签名 | 商户密钥 | 商户私钥 |
| 业务后端验证响应／通知 | 用商户密钥验证通知签名 | 平台公钥 |

业务网站在下单时提交完整的 `notify_url`、`return_url`。它们的协议、域名和端口应分别与 PerPay 中保存的通知来源、返回来源一致。V2 业务后端用商户私钥签名请求，用平台公钥验证 PerPay 的响应和通知；平台私钥由 PerPay 保存。

新网站默认开启 V1/V2 并生成对应凭据。启动时也会初始化尚无易支付配置的历史网站；已有协议开关和凭据保持原值。关闭某一协议的接单开关后，该协议的历史订单仍可查询、发送通知和返回商家。暂停网站通知会保留任务，恢复后继续处理。

修改协议开关后先保存，再管理密钥。密钥在独立弹窗中查看、复制，内容最多显示 60 秒。V2 商户和平台密钥分别更换，更换后同步更新业务端相应配置。易支付使用本页列出的密钥，原生 API 密钥和通知密钥另行管理。

## 接口

| 用途 | V1 | V2 |
| --- | --- | --- |
| 页面下单 | GET/POST `/submit.php` | GET/POST `/api/pay/submit` |
| API 下单 | POST `/mapi.php` | POST `/api/pay/create` |
| 单笔查单 | GET/POST `/api.php?act=order` | POST `/api/pay/query` |
| 商户信息 | GET/POST `/api.php?act=query` | POST `/api/merchant/info` |
| 订单列表 | GET/POST `/api.php?act=orders` | POST `/api/merchant/orders` |

POST 使用 UTF-8 的 `application/x-www-form-urlencoded` 表单。页面下单成功返回 `302` 并跳转 PerPay 收银台；JSON 业务响应使用 HTTP `200`，还需读取 `code` 判断结果：

- V1 成功为 `code=1`，API 下单返回 `trade_no`、`payurl`。
- V2 成功为 `code=0`，API 下单返回 `trade_no`、`pay_type=jump`、`pay_info`；`pay_info` 是收银台地址。
- 失败为 `code=-1`，`msg` 说明原因。V2 验证商户身份成功后，会用平台私钥为响应签名，包括之后发生的业务错误；商户身份验证失败的响应不含可用的平台签名。

### 下单参数

| 参数 | 规则 |
| --- | --- |
| `pid` | 当前网站的固定商户号，按字符串传递。 |
| `out_trade_no` | 商户订单号，1–64 个 ASCII 字符，以字母或数字开头，后续可用字母、数字、`.`、`_`、`-`。 |
| `name` | 商品名称，最多保存 127 个 UTF-8 字节，按完整字符截断。 |
| `money` | 商品原价，单位元，最多两位小数的正数字符串，如 `10.00`。 |
| `notify_url` | 必填，完整 HTTPS 通知地址。 |
| `return_url` | V1 页面下单必填，其他下单方式可选。 |
| `type` | API 下单必填 `alipay`；页面下单可省略。 |
| `method` | V2 API 下单必填 `web` 或 `jump`。 |
| `param` | 可选自定义字符串，随通知和返回请求原样带回；最多 4096 个 UTF-8 字节，不含控制字符。 |
| `timestamp` | V2 必填，当前 Unix 秒时间戳，允许前后 300 秒偏差。 |
| `sign`、`sign_type` | 按下一节计算；V1 使用 `MD5`，V2 使用 `RSA`。 |

同一网站重复提交相同商户单号和业务内容时，会返回原订单。重试时保留原金额、截断前商品名、通知地址、返回地址、`param` 和协议；V2 每次更新请求时间戳并重新签名。使用原单号却改变这些内容会产生冲突。结果未知时先查原单，再重试原请求。

### 查询参数

V1 查询使用 `pid`、`key` 和 `act`。V2 查询由商户后端使用私钥单独签名，公共参数为 `pid`、`timestamp`、`sign`、`sign_type`：

| 查询 | 额外参数 |
| --- | --- |
| 单笔查单 | `trade_no` 或 `out_trade_no`，同时提供时优先 `trade_no`。 |
| 商户信息 | 无。 |
| V1 订单列表 | `page` 从 1 开始；`limit` 默认 20，最大 50；可选 `status=0/1`。 |
| V2 订单列表 | `offset` 从 0 开始；`limit` 默认 20，最大 50；可选 `status=0/1`。 |

查询仅覆盖当前网站的易支付订单。`status=1` 表示当前收款已确认，`status=0` 表示当前未确认，筛选在分页前执行。单号始终按字符串处理。

调用 V2 三个查询接口时，用上表字段和公共签名字段单独构造请求，再重新签名；直接复制下单参数会被拒绝。页面下单和 API 下单可以接收已签名的扩展字段。

商户余额返回 `0.00`，结算关闭。退款、关闭订单、代付和结算兼容接口返回不支持错误。

## 签名与编码

先将表单解码一次，再按参数名的 UTF-8 字节顺序排序，以 `key=value` 连接各项，项间使用 `&`。签名原文中的值不再做 URL 编码：

- **V1**：排除 `sign`、`sign_type` 和空值，在原文末尾直接追加商户密钥，计算小写 MD5。
- **V2**：排除 `sign`、`sign_type` 和空白值，用 RSA-SHA256、PKCS#1 v1.5 签名，结果为 Base64。密钥至少 2048 位，可用 PEM 或单行 Base64。

字符串 `0` 参与两种签名。V1 的纯空格值参与签名，V2 的纯空格值跳过；非空值保留原内容。V2 按 PHP SDK 的方式处理响应：跳过数组和对象，包括列表响应的 `data` 数组，其余符合上述规则的字段参与签名。

发送表单时再做 URL 编码。中文、空格、`+`、值中的 `=` 和字面量 `%26` 可传输；字面量 `+` 编码为 `%2B`。同名字段重复、数组参数和 GET/POST 同名字段冲突会被拒绝。参数名不能含 `&` 或 `=`，参数值不能含字面量 `&`，完整回调 URL 也受此规则约束。

## 付款通知与返回

付款确认后，PerPay 向 `notify_url` 发送 GET 请求，参数包含 `pid`、`trade_no`、`out_trade_no`、`type=alipay`、`trade_status=TRADE_SUCCESS`、`name`、`money`、可选 `param` 和签名。V2 使用平台私钥签名，并附带本次发送时生成的 Unix 秒时间戳，业务端使用平台公钥验签。

`money` 始终是商品原价。例如商品 10.00 元，收银台要求付 10.03 元，查询和通知返回 `10.00`；PerPay 按实际应付的 10.03 元匹配流水。

接收端先验签，核对 PID、商户单号、平台单号和原价，再把付款结果和发货、充值等处理任务写入数据库，保证同一订单不会重复处理。保存成功后，返回 HTTP `2xx` 和文本 `success`，正文首尾空白可忽略。PerPay 根据响应状态决定重试或停止，具体分类和尝试上限见 [USAGE](../USAGE.md#5-回调通知)。

付款人持有该订单的收银台令牌，才能使用“返回商家”。当前收款已确认时，返回 URL 带签名的成功参数；其他状态返回原商家地址。处理浏览器返回和服务端通知时，应查询同一份订单处理记录，避免重复发货或充值；返回页面也可主动查单确认最新状态。

通知和返回地址可设置如 `?tracking_id=123` 的静态参数，静态参数会与支付参数一起签名。参数名须唯一，不能占用支付协议字段，也不能含点号、空格或方括号；静态值同样遵守上一节的编码规则。历史通知地址不符合规则时会记录为永久失败；历史返回地址不符合规则时仍可返回原页面，但不附加付款成功参数。

原付款确认撤销后，对应易支付成功通知停止发送，发送历史继续保留，后台不再提供重发入口。管理重发接口对该事件的新请求返回 `409 / webhook_payment_confirmation_revoked`。重新确认收款会产生新的确认事件和通知；业务网站通过查单核对当前状态。

## 用示例程序检查接入

[Node.js 示例](../examples/node-client/README.md)支持 `PAYMENT_PROTOCOL=native/epay_v1/epay_v2`，可用来核对下单、通知和同步返回。按接入助手中查看、复制的参数填写 `.env` 后启动。

管理员 API `POST /api/admin/v1/sites/:clientId/integration/export` 可导出该示例的 `.env`。请求携带 `protocol`、`site_revision`、`epay_revision`、完整 `notify_url` 和可选 `return_url`；这些地址写入导出文件，不保存为网站设置。文件含密钥，应保存在业务后端。

与 PHP V1.3、V2.0 SDK 和 `go-epay v0.0.5` 实际联调所用的版本、命令和结果见 [SDK 联调记录](../scripts/validation/epay/README.md)。
