**当前口径**

- 超时 raw 由两个父编辑器持有，dirty/error 直接由 raw 推导；没有新增 `onDraftStateChange`。自动 `applyReview` 或应用无关字段冲突必须保留非法 raw、错误及保存阻断；明确选择并应用超时字段的冲突值后才归一化。保存成功和确认放弃另按各自流程同步。
- 新测试订单用「测试订单」；管理员幂等 fallback 与兼容测试必须保留旧固定名称「配置测试支付（真实收款）」。历史名称和指纹不改，普通订单及其他请求字段检查不放宽。
- 发布锁与数据库维护锁是两类锁。发布锁使用 Compose 默认 backup runner，检查对外字段原本就是 `cleanup_eligible`；内部函数或显式 database maintenance CLI 才使用 `cleanupEligible`，此前 review 将 snake_case 判错是遗漏适配层的误判，现已撤回。数据库维护锁需显式 `--entrypoint node maintenance dist/database/maintenance.js`，检查返回 `token`、`operation`、`createdAt` 等记录，不带清理资格字段，也不套用发布锁超过 7 小时等门槛。CLI 协议不改。
- 普通应用租约与 `maintenance` 租约分别解释；维护中断可能留下 24 小时占用，不能承诺等 30 秒必然释放，也不绕过保护。
- AA-11 API 字段改名、AA-17b 数据覆盖截止时间均暂缓；只显示「最近查账成功」，不把 `last_success_at` 或推算窗口当成已覆盖时间。AA-18 已采用「请在支付宝中核对收款方」，不新增或推造商户名。
- OpenAPI 已决定保留 81 个英文、27 个含中文 summary，只统一术语和资源说明；不批量翻译或新增单一语言检查。开发文档仅 `web/README.md`，其他内部报告不纳入。
- 支付宝提供账单与响应签名；PerPay 在本地生成验签结论。候选提示按当前候选/订单状态区分待处理与历史决定，不能统一要求已选用记录再次确认。

## 3. 为什么读起来「不说人话」：五个模式

1. **一句里塞多个条件**
   例：`USAGE.md:67`、`docs/alipay-setup.md:28`、`Sites.tsx:560`。
   改法：一句只留一个主句，条件拆成短句或列表。

2. **双重/三重否定**
   例：「不代表…也不会…」「不是…也不是…不需要…」「不能据此判断未曾投递」「生成密钥不自动开启通知，保存配置也不自动生成密钥」。
   改法：先说「是什么/会怎样」，再说「不是什么」。

3. **内部名词直接外露**
   例：实例、采集、账本、候选、归属、证据、就绪、代次、墓碑、租约、原子切换、金额槽位。
   改法：界面用用户词；文档首次出现给一句定义；同一概念只用一个词。

4. **抽象主语和被动语态**
   例：「系统返回了运行告警，但未提供可定位的原因」「此检查不影响收款」「配置正在应用」。
   改法：主语换成「你」或具体对象：「如果看到这条提示，说明…」。

5. **免责声明堆在正文里**
   例：几乎每个功能说明后面都跟一句「不代表…」「不改变…」「不会…」。
   改法：重复说明可集中到「注意」小节；影响付款、恢复或密钥操作决定的前提仍紧邻动作保留，不能为了精简删除必要边界。

## 4. 建议的改写原则（界面 / 文档两层）

**界面（白话）**

- 标题用名词（「待处理」），按钮用动词（「忽略全部结果」）。
- 一个概念一个词，首次出现给一句解释。
- 状态标签不超过 6 个字，原因放在正文。
- 普通阅读区不堆内部 ID、错误码、表名和字段名，按需放「技术详情」；精确查询、复制或恢复操作需要的编号保留并标明来源。
- 危险操作才用红色警告；普通说明不用「禁止/不得」。

**文档（技术）**

- 每节开头先给「这一节解决什么问题」，再给步骤。
- 步骤编号不超过两级；每步只做一件事。
- 术语第一次出现用「中文（English / 字段名）」格式，之后只用中文。
- 把「限制/边界」集中到每节末尾的「注意」，不要散落在步骤里。
- 迁移历史、schema 版本、内部实现移到维护文档。
